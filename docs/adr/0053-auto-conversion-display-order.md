# 自動最適化でも一覧表の上から処理しつつ先読みでまとめる

## ステータス

- 承認済み (Accepted)

## 背景・課題

自動最適化は倍率・縮小先ごとにファイルをグループ化し、`BatchScheduler` がグループを
順番に消化していた（ADR 0049）。そのため、一覧表で上のファイルが2倍・途中が4倍・
下が2倍のように倍率が混在すると、後ろにある2倍のファイルが先に処理され、
一覧表の表示順と処理順が大きくずれていた。

グループをやめて一覧表で連続する範囲だけをまとめると、表示順は厳密になるが、
倍率が交互に入れ替わるフォルダでは1ファイルごとにプロセスを起動することになり、
モデル読み込みとMoltenVK初期化の固定費が増える。

1プロセスは1倍率しか扱えないため、「厳密に上から順」と「プロセス起動回数を増やさない」は
完全には両立できない。

## 決定

- `BatchScheduler` は、一覧表で最も上にある未処理ファイルを含むグループから
  次のバッチを選ぶ。
- そのグループのファイルのうち、先読み `upscaleLookahead` 件（8件）以内にあるものを
  最大 `upscaleBatchSize` 件（4件）まで1バッチにまとめる。
- 先読みの範囲を超えて後ろのファイルをまとめない。飛び越しは最大8行に収まる。
- 連続する同じグループは、従来どおり最大4件までまとめる。
- 待機から再開したら、先頭のファイルと先読み範囲を必ず選び直す（ADR 0052）。
- 一覧表の行順は `TargetFiles.list` のファイル名順のままとし、表示側は変更しない。

## 代替案

- 一覧表で連続している同じ倍率だけをまとめる（前案）
  - 却下: 表示順は厳密になるが、倍率が交互に入れ替わるとプロセス起動回数が増える。
- グループを順番に消化する（ADR 0049 の当初案）
  - 却下: 後ろのファイルが先に処理され、一覧表の順序と大きくずれる。
- 内部はグループ単位で処理し、表の表示だけ上から順に見せる
  - 却下: 実行中の行と実際に処理しているファイルがずれ、状態表示として誤解を招く。

## 結果

- 2倍と4倍が交互に並ぶ8ファイルの例では、2プロセスで処理しつつ、
  最初のバッチはindex 6までに収まる。
- 同じ倍率が連続する場合は、従来どおり最大4件を1プロセスにまとめる。
- 先読み8件以内の前後入れ替わりは起こり得る。厳密な上から順ではなく、
  「8行以内の範囲でまとめる」ことを許容する。
- 実装箇所: `Services/BatchScheduling.swift`、`Services/ConvertOrchestrator.swift`。
  テスト: `TreeImageOptimizerTests/ConvertPipelineTests.swift`。
