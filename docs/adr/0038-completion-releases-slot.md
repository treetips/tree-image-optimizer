# 処理枠を出力完了でしか空かさない

## ステータス

- 承認済み (Accepted)

## 背景・課題

ステージ別ワーカー（ADR 0034）とディレクトリ一括実行（ADR 0035）を導入したことで、
アップスケールワーカーは前バッチのアップスケールが終わるたびに次のバッチを受け取っていた。
処理枠（並列数）が「アップスケールの完了」で空いていたため、次のような状態になっていた。

- 出力が終わっていないファイルが `並列数` を超えて積もる。
  並列数6で最大12件程度まで開始済み・未完了のファイルが増える。
- 1ファイルの `アップスケール` が終わると、そのファイルの残り（圧縮・出力）が
  終わる前に次のファイルの `アップスケール` が始まる。

画面の並列数は「同時に処理しているファイル数」と読まれるため、
出力完了を完了として扱う必要があった。

## 決定

- `FileBatcher` に処理枠（`capacity = 並列数`）を持たせる。
- スロットは `fileDone` が true の通知でしか返さない。すなわち
  - `出力` の完了（成功）
  - どの段階での失敗
- アップスケールの完了ではスロットを返さない。
- 次のバッチは空き枠の数だけ受け取る（最大 `upscaleBatchSize` の4件）。
  空きが1件も無いときは空きが出来るまで待つ。
- スロットの解放は完了通知に一本化する（`ConvertOrchestrator.trackingOutcome`）。
  各処理箇所から呼ぶと1ファイルで二重に返す、または取りこぼす危険があるため。

## 代替案

- アップスケールの完了でスロットを返す（従来）
  - 却下: 並列数を超え、出力前に次の処理が始まる。
- バッチを必ず4件そろえてから次のバッチを渡す
  - 却下: 空き1件で次が始まらず、「1件の完了で次を開始する」を満たせない。
- ステージごとに並列数を割り当てる（例: アップスケール6・圧縮6）
  - 却下: 合計が並列数を超え、画面の同時処理数が設定値と一致しない。
- 出力完了を待ってから前バッチ全体の次のバッチを渡す（バッチ単位の完了待ち）
  - 却下: 圧縮が遅いとGPUがそのまま止まり、ADR 0034 で解消した待ちを再発させる。

## 結果

- 開始済みで未完了のファイルが `並列数` を超えず、1件の `出力` が終わるたびに
  次の1件が開始される。
- 中間PNGの一時ディスク使用量も `並列数` で頭打ちになる。
- 処理枠が埋まっていると、次のバッチは空き枠ぶんの小さなバッチになる。
  プロセス起動回数が増える場合があり、ADR 0035 の効果が薄れる。
  ただし初期投入時やアップスケールがボトルネックのときは従来どおり4件まとめになる。
- 失敗したファイルも枠を返すため、失敗が続いても処理が止まらない。
