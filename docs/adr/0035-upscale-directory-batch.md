# アップスケールをディレクトリ一括実行にまとめる

## ステータス

- 承認済み (Accepted)

## 背景・課題

従来は画像1枚ごとに `upscayl-bin` または `realcugan-ncnn-vulkan` を起動していた。
どちらのバイナリも起動時にモデルを読み込み、MoltenVKを初期化するため、
1ファイルあたり約0.4秒の固定費がかかる。小さな画像が連続するほど、
この固定費が処理時間に占める割合が大きくなっていた。

両バイナリは `-i` / `-o` にディレクトリを受け付け、複数ファイルを1プロセスで
まとめて処理できる。

## 決定

- 最大4ファイルを1バッチとして、1プロセスでまとめてアップスケールする。
- バッチごとに一時ディレクトリを作り、入力ファイルを `0000.png` のような
  連番へhard linkする。hard linkできない異なるボリュームのときだけコピーする。
- シンボリックリンクは使わない。`upscayl-bin` のディレクトリ走査で
  シンボリックリンクが無視され、出力が作られないことを実測で確認したため。
- プロセスの終了コードだけに頼らず、出力ファイルの存在と寸法をファイル単位で検証する。
  バッチ内の1件が失敗しても、出力が揃っているファイルは成功として後段へ流す。
- Real-CUGANのモデル事前検証はバッチごとに1回だけ行う。
- バッチサイズは4に固定する。

## 代替案

- プロセスを起動したまま次のファイルを流し込む常駐ワーカー
  - 却下: 両バイナリは1回の実行で終了するワンショットCLIで、
    標準入力から追加ファイルを受け取るプロトコルがない。
- 一時入力ディレクトリにシンボリックリンクを張る
  - 却下: `upscayl-bin` のディレクトリ走査で無視される。
- バッチサイズを大きくして起動回数をさらに減らす
  - 却下: `ProcessRunner` はプロセス終了後にパイプを読むため、
    標準出力がパイプ容量を超えるとデッドロックする。また後段の圧縮が
    動き出すまでの待ち時間も長くなる。4件なら出力量と待ち時間の両面で安全。
- 入力をすべてコピーする
  - 却下: 入力の読み書きが増える。同一ボリュームではhard linkで追加I/Oを避ける。

## 結果

- プロセス起動回数がファイル数からバッチ数（約1/4）へ減り、
  モデル読み込みとMoltenVK初期化の固定費を分散できる。
- アップスケールの進捗表示はバッチ単位になる。バッチ内の各ファイルは
  実行開始時に「実行中」、検証完了時に成功・失敗が確定する。
- 一時領域に入力のhard linkを作るため、同一ボリュームでは容量を消費しない。
  異なるボリュームでは入力サイズ分だけ一時的にコピーされる。
