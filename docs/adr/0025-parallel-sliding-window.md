# 一括変換の並列実行をスライディングウィンドウ方式にする

## ステータス

- 承認済み (Accepted)

## 背景・課題

`ConvertOrchestrator.run` は対象ファイルを並列数ずつのバッチに分割し、
`withTaskGroup` でバッチ内の全タスク完了を待ってから次のバッチを実行していた。
そのため20ファイル・並列数10の変換では、途中で先に完了した分の枠が遊んだまま、
バッチ内のもっとも遅い1件の完了まで次のファイルが始まらなかった。

一方、仕様 `docs/design/feature/convert-flow/convert-flow.md` の
「並列処理の単位」は「並列数が3の場合、aaa.jpg か bbb.jpg の一連の処理が
終わったら ccc.jpg の処理が始まる」と定めており、実装が仕様と一致していなかった。

## 決定

- `ConvertOrchestrator.runParallel(count:workers:operation:)` を新設し、
  スライディングウィンドウ方式で実行する。
  - 最初に並列数ぶんのタスクを投入する。
  - 完了が1件返ってくるたびに、未処理ファイルを直ちに1件投入する。
  - 未処理が尽きたら、実行中のタスクの排水を待って完了する。
- `run` からバッチ分割のループを削除し、`runParallel` へ委譲する。
- スケジューラはファイル種別に依存しないため、`Int` インデックスと
  `Bool` 戻り値の汎用クロージャAPIとしてテストから直接検証できるようにする。

## 代替案

- バッチ方式のまま、バッチ内で先に完了した分だけ次バッチを前置する
  - 却下: バッチをまたぐ部分的な再投入になり、常に並列数を維持できず
    分岐が複雑化する。スライディングウィンドウのほうが単純。
- 並列数ぶんのワーカータスクが共有カウンタから次のインデックスを取得する方式
  - 却下: 可変状態へのアクセスにロックが必要になり、タスクグループの
    `next()` で結果を1件ずつ受ける方式より重い。ワーカー数がCPUコア数程度なら
    実害はないが、グループ方式で十分なため排除。

## 結果

- 並列数が10なら余りがない限り10件が常に実行中になる。
  途中完了が出ても即座に次のファイルが投入され、全完了待ちの空転がなくなる。
- 処理順は投入順（ファイル一覧のソート順）を維持する。
  進捗表示の `FileOutcome.index` も各ファイルの位置のまま変わらない。
- 実装箇所: `TreeImageOptimizer/TreeImageOptimizer/Services/ConvertOrchestrator.swift`
