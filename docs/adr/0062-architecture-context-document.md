# アーキテクチャ俯瞰ドキュメントとして CONTEXT.md を整備する

## ステータス

- 承認済み (Accepted)

## 背景・課題

リポジトリには `docs/CONTEXT.md` が存在していたが、**0行の空ファイル**だった。

一方でプロジェクトの情報量は増え続けており、新規参加者（および別の作業を担うエージェント）が
全体像を掴むのに必要な情報が分散していた。

- ADR が56件あり、判断の理由は記録されているが一覧から全体像は読み取れない。
- `Services/` に約20本、`Core/` に10本超のファイルがあり、対応関係がコードを読まないと分からない。
- 設計情報は `docs/design/` に画面仕様としてまとまっているが、「実行時の流れ」と「設定の保存先」のような
  横断的な事項は複数ファイルにまたがっている。
- ADR は「なぜそうしたか」を記録する場であり、「今どうなっているか」をまとめて書く場が無かった。

結果として、変更を加えるたびに `UpscaleService` や `ConvertOrchestrator` を読み直す必要があり、
前提（例: 入力は静止画のみ）を知らずに変更してしまう危険があった。実際に ADR 0062 の調査では、
`postVerify` が静止画前提であることがコードコメントから読み取れず、別途実装を追う必要があった。

## 決定

`docs/CONTEXT.md` を「**現在のアーキテクチャ俯瞰**」として整備する。ADR と役割を分け、
ここには**判断の理由ではなく現在の事実**を書く。

構成は次のとおり。

1. プロジェクトの目的
2. 全体アーキテクチャ（App / View / Model / Service / Core の責務分担と状態管理の要点）
3. 変換パイプラインの流れ（ステージ別ワーカー、処理枠、並列数の扱い）
4. 主要コンポーネントの対応関係（`ConvertOrchestrator` / `UpscaleService` / `CompressionService` / `ConvertJobStore` / `ConversionSettings` 等）
5. 外部ツールの同梱とインストールの仕組み（`ToolInstaller`、`tools/` 配下のバイナリ）
6. 設定の保存（`~/.config/tree-image-optimizer/settings.json`）
7. 対応フォーマット（入力・出力）
8. 開発フロー（lint / format / build、ADR 運用、prek hooks）
9. 関連ドキュメントへのリンク

記述方針:

- **実装を読んで確認した事実のみ**を書く。推測で書かない。
- 各セクションから該当する ADR へリンクし、理由を知りたい場合は ADR へ誘導する。
- コードの具体的な定数値（`upscaleBatchSize = 4` 等）は書かず、挙動と責務を書く。
  値はコード側が正であり、ドキュメントに複製すると乖離するため。
- Markdown は `rumdl` でフォーマット・lint する（ADR 0043）。

## 代替案

- **ADR に俯瞰を書く**: ADR は時系列の決定記録であり、最新の全体像を維持する場として
  不向き。決定が増えるほど古い記述との矛盾が増える。
- **README.md に統合する**: README は利用者向けの導入（インストール・設定・スクリーンショット）であり、
  開発者向けの内部構造を混ぜると両者が読みにくくなる。README からリンクする形に留める。
- **docs/design/system.md を拡充する**: system.md は「こう設計する」という設計方針の記述であり、
  現状のファイル配置やコマンドといった事実の俯瞰とは性格が異なる。併存させ、CONTEXT から参照する。

## 結果

- `docs/CONTEXT.md` が空ファイルから、実装に基づく俯瞰ドキュメントになった。
- 新規参加者は CONTEXT → `docs/design/` → ADR の順に辿れるようになった。
- ADR 0062 の判断時に、入力が静止画のみという前提が CONTEXT にも明記され、前提条件の共有漏れを防げる。
- コード変更時に値まで書いていないため、CONTEXT が陳腐化しにくい構造になった。
  一方で責務分担やファイル配置が変わった場合は更新が必要で、その検出は人手に依存する（残課題）。
