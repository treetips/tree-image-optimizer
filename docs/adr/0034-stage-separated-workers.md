# アップスケールと圧縮をステージ別ワーカーに分ける

## ステータス

- 承認済み (Accepted)

## 背景・課題

従来は1ファイルの `アップスケール -> 圧縮 -> 出力` を1ワーカーが直列に担当していた。
アップスケールはGPUバウンド、圧縮はCPUバウンドで性質が異なるため、
同じワーカーの中で片方が動いている間、もう片方の資源が遊んでいた。

ファイル単位のスライディングウィンドウ（ADR 0025）でも、たまたま処理段階が
階段状に重なるときだけGPUとCPUが同時に動く。並列数やファイルサイズによっては
GPUの待ち時間やCPUの空きがそのまま全体の処理時間になっていた。

## 決定

- アップスケール担当と圧縮担当を別々のワーカー群に分け、間をキューでつなぐ。
- 並列数を次のように配分する。
  - アップスケール: `max(1, min(3, 並列数 / 3))`
  - 圧縮: `max(1, 並列数 - アップスケール)`
- GPUワーカーは最大3に抑える。MoltenVKとモデルの初期化で1プロセスあたりの
  メモリ使用量が大きく、GPUメモリを圧迫しやすいため。
- 圧縮ワーカー数をもとにエンコーダのスレッド数を決める（ADR 0033）。
- アップスケールに失敗したファイルはその場で完了扱いにし、成功したファイルだけを
  圧縮キューへ流す。出力の検証はファイル単位で行う。
- 進捗コールバック（`FileOutcome`）の段階と完了通知は従来どおり維持する。

## 代替案

- 1ファイル直列のまま並列数だけ増やす
  - 却下: GPUとCPUが同時に動く時間が偶然に依存し、安定して両方を使えない。
- GPUワーカーを固定3個にし、圧縮をコア数 - 3にする
  - 却下: 並列数の設定値が画面から見て意味を持たなくなる。設定値を総ワーカー数として扱う。
- アップスケール結果を無制限にキューへ積む
  - 却下: 4倍アップスケールの中間PNGが大量にディスクへ溜まり、容量とI/Oを圧迫する。
    アップスケールワーカー数とバッチ数で自然に上限が決まる現方式にする。

## 結果

- アップスケール中も圧縮が進み、圧縮中も次のアップスケールが進む。
- 並列数1でも最低2ワーカー（GPU1・CPU1）で動くため、設定値1の意味が
  「同時に1ファイルだけ」ではなくなる。処理順序はファイル順ではなく完了順になる。
- 進捗表の段階表示は従来と同じ粒度を保つ。
