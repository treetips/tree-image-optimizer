# ツール配布を上流解決型にし、ZIPを再現可能にする

## ステータス

- 承認済み (Accepted)

## 背景・課題

Release Tools は `tools-latest` の事前リリースを1つだけ更新する。しかし、従来はリポジトリ内のバージョンと既存manifestを比較するだけで、上流の最新版を確認しなかった。このため、Release Tools を定期実行しても、リポジトリ内のツールが更新されない限り配布物は変わらなかった。

また、ZIP生成に `ditto` を使っていたため、checkout日時などのメタデータがZIPへ含まれ、同じバージョンの `force` 再公開でチェックサムが変わることがあった。既存assetの上書き保護は、同名版の内容を無断で差し替えないために必要だが、再現性のないZIPでは正常な再公開も失敗していた。

## 決定

- Release Tools は7ツールの上流最新バージョンを解決し、既存の `tools-info.json` と比較する。
- バージョン・必須asset・Release状態に変更がなければ、buildとpublishをスキップして正常終了する。
- 更新がある場合だけ、解決済みバージョンを使って変更されたツールを取得し、`tools-latest` の事前リリースを更新する。変更されないツールは公開中assetとmanifestを再利用する。定期実行の設定は別途行う。
- macOS用assetがあるツールは上流から取得する。libjxlとlibavifは、ADR 0056とADR 0037のビルド方針をmacOSランナー上で再現する。現行版を再公開する場合は、検証済みのリポジトリ内バイナリがmacOS 26.0以下に対応していれば再利用し、非対応なら再ビルドする。
- ソースビルドはarm64・macOS 26.0を明示し、依存dylibの再配置、deployment target、実際のエンコードを検証する。変更されないツールは再ビルドしない。同版を強制再公開する場合は、リポジトリ内バイナリが非対応なら再ビルドする。
- ZIPはPythonの `zipfile` で生成する。エントリ順をソートし、タイムスタンプ・権限・圧縮方式を固定する。ZIPルートは従来どおり `<tool-name>/` とする。
- preflightはmanifestのSHA-256とRelease assetのdigestを照合し、壊れた配布物を更新なしとして扱わない。
- 通常公開では、同名assetのチェックサムが異なる場合は失敗する。ただし、既存manifestとremote assetのchecksumが一致する同版assetは再利用する。`force=true` の場合だけ明示的な上書きを許可する。
- ツールの実内容を変える場合は、バージョンも変更する。クライアントはバージョンだけを更新判定に使うため、同版の内容差を通常の更新として扱わない。

## 結果

- 更新なしの実行はGitHub Releaseを変更せず、成功として終了する。
- 上流に更新があれば、手動実行でも定期実行でも同じ判定ロジックで配布物を更新できる。
- checkout日時に依存しないチェックサムになり、再実行時のZIPが安定する。
- 取得・ビルド・検証に失敗した場合は公開前に停止し、壊れた配布物をmanifestへ切り替えない。

## 代替案

- リポジトリ内のバージョンだけを比較する: 上流更新の検出を別処理に依存し、Release Tools単独では定期更新できないため不採用。
- 同名assetを常に上書きする: 同版の誤差や改ざんを検出できないため不採用。
- `ditto` のままメタデータを調整する: エントリ順やランナー依存まで制御しにくいため不採用。
