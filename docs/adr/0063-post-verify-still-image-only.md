# アップスケール出力検証は静止画のみを対象とし、マルチフレームは検証で落とす

## ステータス

- 承認済み (Accepted)

## 背景・課題

`UpscaleService.postVerify(output:input:scale:)` と、それが使う
`UpscaleService.imageDimensions(of:)` は、
`CGImageSourceCopyPropertiesAtIndex(source, 0, nil)` で**先頭フレーム（index 0）の寸法**しか読んでいなかった。

そのため次の2つの問題があった。

1. **見逃し**: GIF / APNG / HEIF のようなマルチフレーム入力では、2枚目以降のフレームが
   正しく処理されていなくても、先頭フレームさえ合っていれば検証が通ってしまう。
2. **誤検出**: 逆に先頭フレームだけがおかしい場合、他のフレームが無事でも全体が失敗になる。

`postVerify` は `realcugan-ncnn-vulkan` がモデル不在時に**終了コード0で黒画像を出力する**挙動を
成功扱いにしないための検証である。ここが緩いと黒画像がそのまま圧縮・出力へ流れる。

前提を確認すると、呼び出し側（`ConvertOrchestratorWorkers.enqueuePrepared`）は
アップスケールバッチの出力を**ファイル単位**で検証する経路で `postVerify` を呼んでおり、
入力は常に `TargetFiles.supportedExtensions`（`jpg` / `jpeg` / `png` / `webp`）で選別済みだった。

## 決定

**静止画専用と割り切り、マルチフレーム入力は検証で明示的に落とす。**
全フレーム検証は行わない。

具体的には次のようにした。

- `imageFrameCount(of:)` を追加し、`CGImageSourceGetCount` で総フレーム数を取得する。
  読めない画像（0枚）は nil にして「デコードできない」として扱う。
- `postVerify` は入力の総フレーム数を検査し、**1でなければ `AppError.verificationFailed` で落とす**。
  黙って通さず、前提が崩れたことを明示的に失敗にする。
- `TargetFiles.supportedExtensions` に「静止画のみ」である根拠をコメントで明記し、
  `UpscaleService` 側の前提と対応関係を残す。
- 寸法の読み出しは index 0 のままとする（静止画では index 0 が唯一のフレーム）。

### 全フレーム検証を採らない理由

全フレームを検証するには、各フレームを `CGImageSourceCreateImageAtIndex` で実際に
デコードして寸法を比較する必要がある。これには次の問題がある。

- **コスト**: 一括変換は対象が数千枚になる。フレームごとのデコードは
  アップスケール本体より検証の I/O と CPU が高くつき、検出したい失敗
  （モデル不在による黒画像）に対して釣り合わない。
- **検出対象がズレる**: 検証の目的は「黒画像・欠損・寸法不一致」の検出であり、
  アニメーション各フレームの内容保証ではない。目的に対して過剰な検査になる。
- **出力側が静止画**: 外部アップスケーラ（`realcugan-ncnn-vulkan` / `upscayl-bin`）は
  アニメーションをマルチフレームとして扱わず静止画として読み出す。
  全フレームを検証しても、出力は1フレームなので「入力フレーム数 == 出力フレーム数」の
  比較は成立せず、検証として意味をなさない。

つまり**アニメーション対応そのものが範囲外**であり、その前提を崩さないことを優先した。

## 代替案

- **全フレーム検証を実装する**: 上記のとおりコストに見合わず、出力が静止画である以上
  比較の意味も薄い。アニメーション対応を本格的にやる段階で改めて検討する。
- **現状維持（index 0 のみで何も検査しない）**: マルチフレーム入力が紛れたときに
  黙って見逃す。入力フィルタが静止画のみに絞っていても、
  直接 `postVerify` を呼ぶ経路や将来の拡張で前提が崩れても気づけないため採らない。
- **入力フィルタで `gif` / `heic` を追加してアニメーション対応する**: 変換パイプライン全体
  （アップスケール・圧縮・出力）が静止画前提で組まれており、対応範囲が大きく広がる。
  需要が確認されてから別途判断する。

## 結果

- 静止画の挙動は変わらない。総フレーム数が1の従来どおりの入力は、これまでと同じ検証を通る。
  そのため既存テスト `realCuganPostVerify` は修正なしで通る。
- マルチフレーム入力は「静止画専用」であることを示すエラーで落ちるようになり、
  黙って見逃す挙動がなくなった。
- 新規テスト `realCuganPostVerifyStillImageOnly` を追加し、静止画が通ることと
  マルチフレームが落ちることの両方を確認できるようにした。
- 静止画専用という前提が `TargetFiles` と `UpscaleService` の双方にコメントとして残り、
  `docs/CONTEXT.md` の対応フォーマットにも明記された。
